# read-repo：从仓库任务到关键函数的 HTML 学习页

## 核心目标

给定一个 GitHub/GitLab URL 或本地 repo，交付一个可直接打开的 HTML 学习页，让用户先理解：

1. 这个仓库在做什么任务，面向谁，输入输出是什么。
2. 它做得怎么样：证据、效果、成熟度、限制和风险分别是什么。
3. 为了真正读懂它，应该优先看哪些文件、哪些函数或类。
4. 每个关键函数承担什么职责，和用户可见功能、数据流、模型/算法/服务流程有什么关系。

默认产物是 HTML 页面，不是纯 Markdown 报告。只有用户明确要求时，才只输出文字概要或修改已有页面。

## 工作原则

- 先回答“任务和质量”，再进入“文件和函数”。不要一开始就罗列目录。
- 真实代码优先。所有关键判断必须能追溯到本地文件路径、GitHub/GitLab blob 链接、函数名、类名、测试或论文段落。
- 把“事实”和“推断”分开写。没有源码证据的判断标注为“推断”。
- 默认生成独立 HTML；如果当前项目已有学习页或用户指定目录，则按现有风格插入或新增页面。
- 最终 HTML 学习页必须放在用户指定的长期文档目录中，不要把最终产物留在 `/tmp`。若用户未指定，依次使用 `READ_REPO_OUTPUT_DIR`、`~/Documents/read-repo-learning/`；两者都不可用时先询问。`/tmp` 只用于 clone、缓存、下载、草稿和中间文件。
- 不要生成 placeholder 示例。没有真实样例时，明确写“未在仓库中找到真实样例”。

## 输入处理

1. 如果输入是本地路径，直接在该路径分析。
2. 如果输入是 GitHub/GitLab URL，优先 clone 到 `/tmp/read-repo-<repo-name>/`；如果网络或权限失败，说明原因并请求用户提供本地路径或访问方式。
3. 如果 repo 很大，先用 `rg --files`、`git ls-files`、README、依赖文件和入口文件缩小范围，不要全量通读。
4. 记录当前 commit SHA；生成远程代码链接时尽量固定到该 SHA，而不是浮动的 `main` / `master`。
5. 最终学习页的长期输出路径按以下顺序解析：
   - 用户明确指定的目录或已有学习页项目；
   - `READ_REPO_OUTPUT_DIR/<repo-name>/index.html`；
   - `~/Documents/read-repo-learning/<repo-name>/index.html`。
   - 如果这些位置都不可用，先询问用户；不要写入项目根目录或臆造个人目录。
   - 可以在 `/tmp/read-repo-<repo-name>/`、`/tmp/read-repo-<repo-name>-work/` 等位置存放临时 clone 和中间文件，但完成前必须把最终 HTML 写入或复制到长期目录。

## 阶段 1：先判断仓库任务和完成质量

优先读取：

- `README*`、`docs/`、项目主页、demo、examples。
- 依赖和入口文件：`package.json`、`pyproject.toml`、`setup.py`、`Cargo.toml`、`go.mod`、`pom.xml`、`Makefile`、`Dockerfile` 等。
- 发布、测试、benchmark、eval、examples：`tests/`、`bench*`、`eval*`、`examples/`、`scripts/`。

在 HTML 开头回答：

- 任务：这个项目解决什么问题，属于工具、应用、库、模型、数据管线、研究原型还是生产服务。
- 用户：谁会用它，典型场景是什么。
- 输入/输出：用户或系统给它什么，它产出什么。
- 方法：它大概靠什么技术路线完成任务。
- 做得怎么样：用 README 声明、实验/benchmark、测试覆盖、示例完整度、活跃度、代码组织、错误处理等证据评价。
- 限制：仓库自己承认的限制、代码里体现的限制，以及只基于阅读得到的风险判断。

## 阶段 2：发现论文并接入 read-paper

如果 README、docs、仓库描述或代码注释中出现 arXiv、DOI、论文 PDF、paper title、conference/journal 信息：

1. 判断这篇论文是否是理解仓库核心方法所必需的。只是引用背景文献时，不必精读。
2. 先搜索当前工作区、用户提供目录和常见输出位置中是否已有对应 read-paper 解读文档；如果有，直接读取现有 Markdown，并在 HTML 中引用该文档路径。
3. 如果没有现成解读，使用 `read-paper` skill 研读论文，得到结构化中文解读后再回到 repo 学习页。
4. 在 HTML 中加入“论文背景”区域：论文解决的问题、核心方法、实验结论、与代码模块的对应关系。

如果没有找到中心论文，HTML 中简短标注“未发现与仓库强绑定的论文”即可。

## 阶段 3：定位架构入口和阅读优先级

用 `rg --files` / `git ls-files` 获取文件列表，忽略明显生成物和依赖目录，例如 `node_modules/`、`.venv/`、`dist/`、`build/`、`target/`、`__pycache__/`、大体积数据文件。

按下面优先级建立阅读路线：

- **P0 必读**：主入口、核心任务/算法/业务逻辑、主要 API/CLI/server route、核心数据结构、模型调用、pipeline 编排、端到端测试。
- **P1 应读**：配置、适配器、外部服务封装、数据加载/转换、eval/benchmark、关键脚本、覆盖主流程的测试。
- **P2 需要时读**：样式、文档页面、示例 UI、构建配置、生成代码、迁移脚本、重复模板。

每个条目都写清楚：为什么优先、读它能解决什么问题、后续要跳到哪个文件或函数。

## 阶段 4：函数级精读

对 P0 和重要 P1 文件，提取关键函数/类，而不是停留在文件名层面。优先关注：

- 入口函数：`main()`、CLI command、HTTP route、job handler、pipeline runner。
- 核心处理函数：模型推理、检索、训练、评估、数据转换、状态更新、权限/校验、调度。
- 数据边界函数：load/save、parse/serialize、schema validation、API client、DB access。
- 编排函数：把多个步骤串起来的 controller、service、workflow、orchestrator。
- 测试函数：最能说明预期行为和边界条件的测试。

HTML 中的函数表至少包含：

- 文件路径或远程 blob 链接。
- 函数/类名。
- 它解决的子问题。
- 输入、输出和关键副作用。
- 调用关系：谁调用它，它调用谁。
- 为什么应该读它。
- 如果要改相关功能，大概率会动哪里。

## 阶段 5：生成 HTML 学习页

默认创建一个独立 HTML 文件，建议路径：

```text
${READ_REPO_OUTPUT_DIR:-~/Documents/read-repo-learning}/<repo-name>/index.html
```

如果用户指定已有网站或学习页项目，则在该项目中新增页面或 section，并保持现有视觉风格。

HTML 推荐结构：

1. 顶部摘要：仓库名、链接、commit、核心结论。
2. “它在做什么任务”：用户、输入输出、主要能力、技术路线。
3. “做得怎么样”：证据表、亮点、限制、风险。
4. “论文背景”：仅当存在中心论文时展示，并连接论文观点与代码模块。
5. “代码阅读路线”：P0/P1/P2 文件列表。
6. “关键函数地图”：函数/类职责、调用关系、输入输出、阅读理由。
7. “核心流程 walkthrough”：用真实文件和函数串起主流程。
8. “学完后应该知道什么”：用自然语言总结用户现在能向别人解释的内容。

页面应适合浏览和复习：使用清晰层级、表格、代码路径、轻量交互或锚点；不要写成只有大段文字的静态报告。

## 追溯和验证

完成前检查：

- 已配置长期输出目录中的最终 HTML 文件存在且可直接打开；不要只检查 `/tmp` 中的临时副本。
- 如果生成过程中先在 `/tmp` 写了草稿，确认最终版本已复制或移动到长期目录，并在最终回复给出长期保存路径。
- 每个关键技术判断都带真实文件路径、函数名或远程代码链接。
- 关键文件和函数名用 `rg` 或源码读取确认存在。
- 对 GitHub/GitLab 链接，尽量使用固定 commit 链接。
- 论文相关内容来自 read-paper 结果、论文原文或仓库引用，不凭印象写。
- 没有 `TODO`、`placeholder`、虚构 JSON、虚构函数名。
- 如果只能基于 README 或少量源码推断，HTML 中明确标注证据不足。
